Stub 01 · Decision OS

Odluka prije prve akcije

Decision OS je middleware između agenta i alata. Ne pita model da li je akcija sigurna — izračuna rizik, dodijeli tier, zapiše očekivani dokaz i vrati envelope koji se izvršava ili odbija. Sve deterministički, ispod 3 ms, bez dodatnog LLM poziva.

L0 p50 2.31 ms · jezgro 0.30 ms ECE 0.035 na held-out 4 tiera expected_evidence_spec Apache-2.0 jezgro

Arhitektura

3-Gate zatvorena petlja

Gate 1 odlučuje, Gate 2 izvršava (ili blokira), Gate 3 dokazuje. Nijedan gate se ne preskače.

  agent / LLM
      |  tool_call(text, args)
      v
+------------------------------------------------------------------------------------+
| GATE 1 - L0 DECISION                                                               |
|   deterministic precheck -> classifier -> calibration T=0.2                        |
|   out: tier - verdict - risk - confidence - evidence_spec                          |
|        decision_id + decision_hash (SHA-256)                                       |
+------------------------------------------+-----------------------------------------+
                                           |  DecisionEnvelope
                                           v
+------------------------------------------------------------------------------------+
| GATE 2 - ROUTING + EXECUTION                                                       |
|   READ / DRAFT        -> allow + sandbox by risk                                   |
|   SEND / IRREVERSIBLE -> ask / deny + human approval                               |
|   hard block: destructive commands, even if model says ok                          |
+------------------------------------------+-----------------------------------------+
                                           v
+------------------------------------------------------------------------------------+
| GATE 3 - EVIDENCE GATE                                                             |
|   tool_result -> check against expected_evidence_spec                              |
|   receipt: sha256(result) + link to decision_hash                                  |
|   verified? -> done   :   rollback / escalation                                    |
+------------------------------------------------------------------------------------+

Dijagram je pojednostavljen: approval tok, replay i idempotency su detalji Gate 2/3 i opisani su na stranici SIGIL.

Tiering

Četiri tiera, četiri nivoa dokaza

Tier nije oznaka težine — to je ugovor o tome šta smije da se izvrši i koji dokaz mora uslijediti.

TierTipične akcijeVerdictOčekivani dokaz
READ SQL SELECT, čitanje fajla, pretraga, status allow read_only, sql_rows
DRAFT pisanje fajla, kod, lokalna izmjena, generisanje dokumenta allow (+ sandbox po riziku) file_sha256, code_verified
SEND mail, WhatsApp, objava, poziv prema trećoj strani ask — traži izričitu naredbu external_send + audit hash + primalac
IRREVERSIBLE brisanje, plaćanje, produkcijski deploy, destruktivne komande deny ili ask (uz approval) delete_verified, approval + receipt
Tvrda blokada je stvarna. Ugrađeni precheck hvata destruktivne i obfuskirane komande (npr. base64 pipe u shell) i vraća deny bez pitanja modela. Benigni citat komande („echo 'rm -rf /'") ostaje READ — provjereno testovima.
Ugovor o dokazu

expected_evidence_spec

Prije izvršenja se zapisuje šta tačno mora biti istinito da bi se akcija proglasila uspješnom.

Primjer: slanje maila

{ "kind": "external_send", "requires_explicit_send_verb": true, "must_have_audit_hash": true, "must_record_recipient": true }

Bez eksplicitnog glagola za slanje, bez zabilježenog primaoca i bez audit hasha — nema „poslano".

Primjer: izmjena koda

{ "kind": "code_verified", "must_change_sha256": true, "must_pass_semgrep_diff": true }

Fajl mora stvarno promijeniti hash, a diff mora proći statičku provjeru. Modelov „ok" se ignoriše.

Specifikacija je dio envelope-a i hashirana je u decision_hash, pa se ne može naknadno „ublažiti" da bi akcija prošla.

Kalibracija

Pouzdanost koja se mjeri, ne osjeća

Klasifikator vraća vjerovatnoću; temperatura skaliranje je poravnava sa stvarnom frekvencijom ishoda.

Ograničenje koje ne krijemo: fit je udario u donju granicu (T=0.2) jer je accuracy na ovom setu 1.0 — set je degenerisan za kalibraciju. ECE 0.035 je stoga realan rezultat na held-out dijelu, ali ga ne treba čitati kao garanciju na težim, realnim greškama. Sljedeći korak je re-fit na setu sa stvarnim greškama i objava novog broja — do tada je ovo jedini ECE koji tvrdimo.

Puni eval adaptera prije temperature scalinga: ECE 0.299211, Brier 0.094742, accuracy 1.000, n=1200 (internal evaluation run). Kalibracija je rađena naknadno na istom izvoru, sa fit_method=scipy.bounded.

RLDF petlja

Od near-miss do strože granice

Sistem uči iz akcija koje su bile blizu greške: par „chosen / rejected" ide u DPO, pa u novu kalibraciju i pragove.

01

Detekcija near-miss

Odluka koja je prošla, ali sa niskom marginom ili bez očekivanog dokaza, označava se kao near-miss.

02

Par za DPO

Ispravna akcija (chosen) i skoro-ispravna (rejected) čine trening par; 600 parova, 2 epohe, 36 koraka.

03

Adapter + realni eval

LoRA adapter se evaluira na held-out setu: train loss 0.10052; ECE 0.2992, Brier 0.0947, accuracy 1.0 (n=1200).

04

Kalibracija i pragovi

Temperature scaling spušta ECE na 0.0347; novi pragovi ulaze u Gate 1 tek nakon što prođu iste testove.

RLDF ciklus je dokumentovan u repozitoriju (scripts and two internal evaluation runs). Petlja je namjerno spora: nijedan novi prag ne ide u produkciju bez ponovljenog eval-a.

Kod

Tri poziva za punu petlju

import gama_decision_l0 as D0 # Gate 1 — odluka prije alata env = D0.decide_request("napiši funkciju i snimi u test.py", sid="job-42") # env["tier"] == "DRAFT", env["verdict"] == "allow" # env["expected_evidence_spec"]["kind"] == "code_verified" # Gate 2 — izvršenje (vaš agent ili sandbox) result = run_in_sandbox(env) # Gate 3 — dokaz; receipt nosi decision_hash receipt = D0.verify_evidence(env, "fs_write", result) assert receipt["verified"] is True # metrika: D0.status() vraća calls, cache_hits, evidence_checks, ...
Bez magije: jezgro ne poziva LLM. Kada je potreban semantički sloj, harness ga dodaje kao opcioni spekulativni korak sa strogo ograničenim budžetom — i nikad mu ne daje pravo da snizi tier.
Ograničenja

Šta Decision OS ne radi

Ne zamjenjuje poslovnu logiku

On ne zna da li je cijena ispravna ni da li kupac smije dobiti rabat. On zna da je akcija SEND, da traži dokaz i da bez njega nema „poslano".

Ne garantuje tačnost modela

Kalibracija poboljšava pouzdanost vjerovatnoće, ne istinitost odgovora. Za tačnost su odgovorni model, izvori i verifikator.
